# Практическая работа № 1, вариант 7

Репозиторий: https://github.com/Gartem6/git-practice-1

Я создал репозиторий на GitHub и три его копии: person1, person2 и person3. Они изображают рабочие папки трёх разработчиков. В проекте есть небольшая программа на Python: она считает среднее число паллет на отгрузку, составляет сводку и определяет крупные отгрузки. Для функций написаны тесты.

Изменения из одной папки не появлялись в другой сами по себе. Я сохранял их коммитами, отправлял на GitHub через `git push`, а в другой копии получал через `git pull`.

Я попробовал несколько способов работы с ветками. При обычном `merge` ветки `dev` появился отдельный коммит слияния. При `merge --squash` два изменения README попали в `main` одним новым коммитом. При `rebase` коммит ветки `dev2` был перенесён поверх обновлённой `main` и получил другой хеш. Также я использовал интерактивный `rebase -i`: объединил два коммита с заметками в один.

Изменения трёх «разработчиков» в разных местах файлов Git объединил автоматически. Затем я специально создал ситуацию, когда две ветки меняют одну и ту же строку `main.py`. Git остановил слияние и показал конфликт. Я выбрал итоговый текст строки, удалил метки конфликта и завершил слияние коммитом.

Дополнительно я посмотрел историю через `git log` и `git log -p`, проверил `reset --hard` в отдельной учебной ветке, перенёс один коммит через `cherry-pick`. Из двух коммитов `dev3` создал патчи командой `git format-patch` и применил их к `main` через `git apply`.

По варианту 7 я специально убрал проверку пустого списка в `shipments.py`. Из-за этого тест стал выдавать `ZeroDivisionError`. С помощью `git bisect` я проверял промежуточные коммиты и помечал их как `good` или `bad`. После пяти проверок Git нашёл первый коммит с ошибкой — `b95c2f9`. Затем я выполнил `git bisect reset`, вернул проверку пустого списка и создал коммит с исправлением. Все 10 тестов после исправления прошли.
